# v3.2 Interaction RC1｜Mixed Routing Test Results

> 测试性质：单窗口受控模拟，不是独立多 Agent 外部实验。
>
> 目标：验证 Interaction Router 能否在简单题、标准经营题和高风险题混合出现时，自动选择 QUICK / FULL / HIGH-STAKES QUICK，而不是机械按一种格式输出。

## 测试集（10题）

1. 063｜技术先进但客户一直不付钱，是否继续投入？
2. 042｜大客户信用没问题，但账期从90天拖到180天，是否压缩订单？
3. 059｜区域门店已赚钱，是全国复制还是再验证？
4. 060｜利润不错但设备、厂房、库存占用过多资本，是否外包？
5. 065｜AI项目说不清ROI，但认为未来一定需要，是否先投？
6. 012｜负债7000多万、资金链断裂、220人停工，清算还是救？
7. 028｜借5000万但资金方参与董事会，要不要拿？
8. 021｜1.74亿欧元跨境收购，要不要签？
9. 074｜海外人工便宜，要不要直接建厂？
10. 041｜现金危机下，银行、供应商、工资和生产谁优先？

## 预期路由

- 普通探索型问题：QUICK
- 标准但结构性较强问题：QUICK，必要时升级 FULL
- 高风险且信息不足：HIGH-STAKES QUICK + Minimum Evidence Gate
- 高风险且信息足够支撑完整判断：FULL

## 关键发现

### 1. QUICK 不应该等于 LEVEL 1
Interaction Depth 和 Decision Complexity 是两条不同轴。

一个 LEVEL 3 的重大问题，在信息明显不足时，首轮仍可能适合 HIGH-STAKES QUICK；它的任务不是直接给完整董事会报告，而是先给条件性方向、关键未知数和尾部风险。

### 2. FULL 的触发应该由“信息充分度 + 风险 + 用户意图”共同决定
不是只要金额大就自动 FULL。若事实不足，FULL 反而容易制造伪精确。

### 3. 高风险 QUICK 的本质是“安全压缩”
它保留最会改变决策的变量，而不是保留最多内容。

### 4. Interaction Router 与 Decision Engine 应解耦
Decision Engine 负责把问题想清楚；Interaction Router 只决定首轮展示多少。不得为了 QUICK 改变底层结论。

## 状态判断

**v3.2 Interaction RC1 = SIMULATED PASS**

理由：
- 普通题能显著缩短首轮回答；
- 高风险题未因压缩丢失关键未知数或尾部风险；
- FULL / QUICK / HIGH-STAKES QUICK 三类路由可区分；
- 没有改变 v3.1 的 Decision Engine。

## 发布建议

可以进入 v3.2 Release Candidate 整理阶段，但正式合并 main 时只应修改：
1. Interaction Router；
2. QUICK Renderer；
3. HIGH_STAKES_COMPRESSION_GATE；
4. 输出触发规则。

不得顺带修改 v3.1 Decision Engine、Schema 经济判断字段或视觉设计系统。
